# 《人工智能的网络应用》课程综合项目

**面向网络运行、管理与维护的 AI Agent 设计与实现**

课程综合项目：30 分

## 一、项目目标

本课程已经学习并实践了以下知识与技术：

- **大语言模型与本地部署**：LLM 基本原理、DeepSeek、Ollama。
- **智能体开发**：Agent、Tool、PydanticAI、CrewAI。
- **AI 辅助编程**：Trae、DeepSeek Harness，以及 AI 辅助软件开发方法。
- **Skill Engineering**：通信领域 Skill、专业知识组织与复用。
- **通信领域 Agent**：香农公式计算、无线信道质量评估、调制方式选择。
- **数据分析与机器学习**：数据清洗、数据探索、KNN、决策树、逻辑回归（LR）、GBDT，以及汽车分类小项目。

此前，同学们还通过一系列课堂作业，学习了从真实问题出发，分析用户需求、设计 AI 工具，并借助 AI 完成软件开发的方法。

这次综合项目，希望大家将这些知识连接起来。

**请面向网络运行、管理或维护中的一个真实问题，设计并实现一个能够调用工具、运用网络知识、分析证据，并帮助网络工程师作出判断的 AI Agent。**

项目的核心不是做一个聊天机器人，而是让 AI 真正参与网络工程任务。

我们希望建立如下工作过程：

```text
网络问题 / Incident
        ↓
理解问题与网络状态
        ↓
提出可能的原因 / Hypotheses
        ↓
选择需要的工具 / Tools
        ↓
获取和分析证据 / Evidence
        ↓
应用网络理论与专业 Skill
        ↓
验证或反驳假设
        ↓
形成结论 / Conclusion
        ↓
给出建议 / Recommendation
```

最终，请证明你的 Agent 不仅能够回答问题，而且能够通过使用工具、分析数据和运用专业知识，比直接询问大语言模型做得更好。

---

## 二、项目选题

### 2.1 从一个真实的网络问题出发

项目应当有明确的目标用户和实际应用场景。

请使用下面的句式描述自己的项目：

> 我们希望为【某类网络工程师】开发一个 AI Agent，帮助他调查【某一类具体网络问题】，利用【网络数据、理论模型、工具和专业 Skill】寻找支持或反驳不同假设的证据，最终形成【可解释的调查结论和行动建议】。

例如：

- 为校园网工程师开发网络高延迟调查 Agent，判断异常是来自链路拥塞、路由变化还是其他原因。
- 为无线网络工程师开发 Wi-Fi 性能调查 Agent，判断低吞吐率是由信号质量、干扰还是用户拥塞造成的。
- 为网络规划工程师开发容量分析 Agent，利用排队论评估网络利用率、时延与扩容需求。
- 为路由工程师开发路由异常调查 Agent，分析路由变化、拓扑故障与路径选择。
- 为光网络工程师开发 WDM 光路建立失败调查 Agent，分析波长可用性与路径约束。

### 2.2 参考选题

可以从老师提供的两个项目建议文件中选择题目，也允许结合此前课堂作业自行设计。

建议优先考虑以下几类问题：

| 类别          | 项目方向                         | 可使用的网络知识                   |
| ------------- | -------------------------------- | ---------------------------------- |
| A. 网络性能   | 高 RTT、拥塞、排队时延、突发流量 | Little 定理、M/M/1、时延分析       |
| B. 无线通信   | Wi-Fi 性能、信道质量、调制选择   | 香农公式、SNR、链路预算            |
| C. 路由与故障 | 路由异常、路径变化、故障恢复     | Dijkstra、Bellman-Ford、网络拓扑   |
| D. 流量工程   | 链路负载、容量规划、资源分配     | 需求矩阵、流量工程、公平性         |
| E. 传输网络   | MPLS、SDH、WDM 网络异常          | 逻辑路径、物理路径、容量、波长约束 |
| F. 网络运维   | DNS、DHCP、端口、配置异常        | 网络协议、网络测量、日志分析       |

特别鼓励同学们把上一学期学到的通信网理论，变成 Agent 可以调用的计算工具和专业 Skill。

### 2.3 项目规模与边界

建议每组选择：

- **一类网络问题**；
- **一个具体的用户角色**；
- **一个可运行的最小 Agent**；
- **至少两个具有实际功能的 Tool**；
- **至少一个自己设计或改进的通信领域 Skill**；
- **一组能够检验 Agent 能力的测试案例**。

不要求开发大型网络管理系统，不要求连接真实运营商设备，也不要求训练自己的大语言模型。

可以使用本地 JSON、CSV、网络拓扑、模拟日志、公开数据或安全的实验环境。

**项目应该小而完整，不追求大而复杂。**

## 三、项目必须实现的核心功能

### 3.1 Agent：能够完成多步骤工作

Agent 需要根据用户提出的问题，自主判断接下来应当执行什么操作，并调用合适的工具。

例如：

用户输入：

“某条网络链路的时延由 20 ms 上升到 180 ms，请调查原因。”

Agent 不应该立即回答：

“这是网络拥塞造成的。”

而应该进一步调查：

1. 当前网络有哪些可观测数据？
2. 可能有哪些原因？
3. 应该调用什么工具？
4. 工具返回了什么结果？
5. 哪些假设得到支持，哪些受到质疑？
6. 证据是否足以形成结论？

允许使用 PydanticAI、CrewAI 或其他适当框架，也可以使用轻量级的自主实现。

不要求使用多 Agent 架构。**单个 Agent 只要能够正确调用工具、开展调查并形成可信结论，就符合要求。**

### 3.2 Tool：至少实现两个真实可用的工具

工具应当具有实际功能，而不只是向 LLM 返回一段预先写好的结论。

例如：

| Tool                            | 功能                               |
| ------------------------------- | ---------------------------------- |
| `get_link_metrics`              | 查询链路利用率、时延、丢包等指标   |
| `calculate_queue_delay`         | 根据排队模型和输入参数计算理论时延 |
| `query_routing_table`           | 查询当前路由信息                   |
| `calculate_shortest_path`       | 根据网络拓扑计算最短路径           |
| `analyze_wifi_quality`          | 根据无线测量值分析信道质量         |
| `check_wavelength_availability` | 检查 WDM 路径的可用波长            |

工具可以是自己编写的 Python 函数，也可以通过适当接口访问其他程序。

必须说明工具的输入参数、输出结果、功能边界和错误处理。

至少有一个工具应体现通信、网络或数据分析中的实质性计算或检查。

**不能把所有分析都交给大语言模型在文本中自行完成。**

### 3.3 Skill：至少实现一个网络专业 Skill

参考课堂学习的通信 Skill 和老师提供的通信工程师专家资料，设计或改进一个适合自己项目的 Skill。

Skill 应包含：

1. 适用场景：什么时候使用？
2. 专业知识：需要哪些理论、公式、协议或规则？
3. 工作步骤：按照什么顺序分析？
4. 工具选择：什么情况下调用什么工具？
5. 验证方法：怎样检查分析结果？
6. 常见错误：哪些情况容易误判？
7. 不确定性：什么时候应当承认证据不足？

例如，网络高时延调查 Skill 应明确区分传播时延、传输时延、排队时延和处理时延。

不能仅凭 RTT 升高就认定发生拥塞，还需要检查路径、利用率、队列指标等证据。

Skill 可以采用 `SKILL.md` 及配套资源文件的形式。

**Skill 不是把教材内容复制成 Markdown，而是把专业知识组织成 Agent 可以实际执行的工作方法。**

### 3.4 调查、证据与反证

Agent 应当能够：

- 提出至少两个有意义的候选假设；
- 通过工具获取用于判断的证据；
- 识别支持假设与反驳假设的证据；
- 根据新证据修正判断；
- 在证据不足时明确说明无法确定；
- 给出与证据相符的结论和建议。

对于一些较简单的问题，也允许 Agent 直接完成确定性计算，但综合项目中必须包含可以检验其调查与判断能力的案例。

尤其鼓励：

**不只是让 Agent 找到一个答案，还要检验 Agent 在面对错误线索、矛盾证据或信息不足时是否仍然能够作出合理判断。**

## 四、最终报告要求

报告应包含以下七个部分。

### 第一部分：项目背景与问题定义（建议 400–600 字）

介绍项目的用户、场景和问题。

至少回答：

1. 目标用户是谁？
2. 具体希望解决什么网络问题？
3. 目前工程师如何处理这个问题？
4. 为什么需要 AI Agent？
5. 本项目要实现什么功能？
6. 本次项目明确不解决什么问题？

请给出一个真实或合理模拟的网络 Incident，描述其症状、已知条件和预期的调查任务。

例如：

某校园网络上联链路利用率从 45% 上升至 90%，用户发现网络时延显著增加。Agent 需要调查这一变化是否与排队拥塞有关，并检查其他可能原因。

尽量用具体问题代替“赋能网络运维”“提高智能化水平”等笼统描述。

### 第二部分：系统架构与 Agent 设计（建议 500–700 字）

**必须提供一张自己绘制的系统架构图。**

图中至少展示：

- 用户与交互入口；
- LLM 与 Agent；
- Tool 层；
- Skill / 专业知识层；
- 数据、网络模型或模拟环境；
- 调查结果输出。

建议架构：

```text
          网络工程师
              │
       输入网络问题
              │
              ▼
       AI Agent / LLM
              │
       ┌──────┴──────┐
       │             │
       ▼             ▼
   Domain Skill   Tool Selection
       │             │
       │        ┌────┴────────┐
       │        │             │
       │        ▼             ▼
       │    网络测量工具   理论计算工具
       │        │             │
       └────────┴──────┬──────┘
                       │
                       ▼
                 证据分析与验证
                       │
                       ▼
                结论和行动建议
```

可以采用不同架构，但必须说明各模块如何协作。

重点回答：

1. 为什么选择当前 LLM 和 Agent 框架？
2. Agent 如何决定调用哪个 Tool？
3. Skill 在什么时候被加载或使用？
4. Agent 如何获得工具结果？
5. 如何将工具结果转化为分析结论？
6. 如何处理工具调用失败、无效输入或数据缺失？

建议再提供一张典型任务执行流程图，说明一次调查如何从用户输入走向最终结论。

### 第三部分：Tool 与 Skill 的设计和实现（建议 500–800 字）

**1. Tool 设计**

用表格说明至少两个 Tool 的具体功能。

| 工具名                  | 输入           | 输出                  | 实际作用     |
| ----------------------- | -------------- | --------------------- | ------------ |
| `get_link_metrics`      | 链路编号       | 利用率、RTT、队列数据 | 获取网络状态 |
| `calculate_queue_delay` | 到达率、服务率 | 理论时延              | 验证拥塞假设 |

说明关键输入输出的数据结构，并展示必要的核心代码。

如果采用 PydanticAI，可以展示工具定义与调用方式；如果采用 CrewAI，可以说明 Agent、Task、Tool 之间的组织关系。

如使用 Pydantic 或其他结构化输出机制，应说明输出字段及验证方法。

**2. Skill 设计**

说明 Skill 的名称、内容、文件组织方式，以及它解决什么专业问题。

至少选取一个具体案例，展示：

- 不使用 Skill 时，Agent 如何分析；
- 使用 Skill 后，Agent 的工作过程发生了什么变化；
- Skill 是否帮助 Agent 更正确地选择工具、检查证据或避免错误。

不要仅凭一次成功的演示就声称 Skill 有效，效果应在第五部分进行系统比较。

**3. 专业知识的正确性**

说明使用了哪些网络理论、模型或协议知识，以及适用条件。

例如，M/M/1 模型不能不加说明地适用于所有网络流量；香农容量不等于实际可达到的用户吞吐率；路由路径短也不一定代表符合路由策略。

### 第四部分：Agent 的调查过程与工作实例（建议 500–700 字）

选择一个具有代表性的案例，完整展示 Agent 的工作过程。

建议使用下面的格式：

| 调查步骤 | Agent 的操作  | 获得的信息或结果         |
| -------- | ------------- | ------------------------ |
| 1        | 接收 Incident | 链路时延显著上升         |
| 2        | 提出假设      | 拥塞、路径变化、速率下降 |
| 3        | 调用测量工具  | 获取利用率和 RTT         |
| 4        | 调用计算工具  | 计算理论排队时延         |
| 5        | 证据分析      | 比较测量与理论预期       |
| 6        | 验证反面证据  | 检查路径和速率是否改变   |
| 7        | 输出结论      | 给出有证据支持的判断     |

必须展示至少一次**真实发生的 Tool 调用过程**，包括输入、工具返回值以及 Agent 如何使用该结果。

还应展示：

- 一条支持某个假设的证据；
- 一条反驳某个假设或限制结论的证据；
- 最终分析结论及其依据。

允许使用工具日志、Agent Trace 或运行截图，但需要解释这些内容的含义。

不要求粘贴完整的 LLM 对话历史。

### 第五部分：实验设计、评测结果与分析（建议 700–1000 字）

**这是综合项目评分中非常重要的一部分。**

请设计一组可以复现的测试，回答：

> 使用 Agent、Tool 和 Skill，是否真的比直接询问大语言模型更好？

#### 5.1 测试案例

原则上至少设计 **5 个测试 Case**。

案例应覆盖不同情形，不能全部是同一问题只修改数字。

建议包含：

- 正常情况下可以成功解决的问题；
- 需要使用专业计算工具的问题；
- 包含错误线索或反面证据的问题；
- 数据不完整、无法确定结论的问题；
- 边界情况或容易发生专业误判的问题。

对每个案例，给出输入、可用数据、预期结果或判断标准。

对于模拟案例，应明确说明正确答案如何确定。对于没有唯一答案的案例，应提供合理的评判规则。

#### 5.2 对照实验

尽量使用同一基础模型，进行以下三组对比：

| 实验组 | 系统配置                    | 希望研究的问题                  |
| ------ | --------------------------- | ------------------------------- |
| A      | 直接询问 LLM                | 仅靠模型知识能做到什么程度？    |
| B      | LLM + Agent + Tools         | 工具调用是否带来改进？          |
| C      | LLM + Agent + Tools + Skill | 专业 Skill 是否带来进一步改进？ |

三组实验应尽可能保持模型、测试问题和外部数据条件一致，说明不同实验组可获得的信息范围。

如果某个实验组无法完成任务，应记录失败原因，不能编造实验结果。

#### 5.3 评测指标

至少使用两个有意义的指标。

建议选择：

| 指标           | 说明                                     |
| -------------- | ---------------------------------------- |
| 任务成功率     | 有多少测试 Case 达到预期目标             |
| 结论正确率     | Agent 最终判断是否符合标准答案或评判规则 |
| 工具调用正确率 | 是否选择并正确使用了所需工具             |
| 证据完整率     | 关键判断是否有充分、有效的证据           |
| 反证处理能力   | 是否正确识别矛盾或反面证据               |
| 执行成本       | Token 消耗、调用次数或运行时间           |

不要求使用所有指标，也不要求建立复杂的自动评测平台。

但必须事先说明指标如何计算，避免只凭主观印象打分。

#### 5.4 评测结果

至少提供一张对照结果表和一张分析图。

例如：

| 指标           |    LLM | Agent + Tools | Agent + Tools + Skill |
| -------------- | -----: | ------------: | --------------------: |
| 任务成功率     |      — |             — |                     — |
| 结论正确率     |      — |             — |                     — |
| 工具调用正确率 | 不适用 |             — |                     — |
| 平均运行时间   |      — |             — |                     — |

使用实际实验结果填表。

如果实验允许，建议对同一配置进行多次运行，记录波动，避免只选取表现最好的一次。

#### 5.5 错误案例分析

至少详细分析一个失败或不理想的 Case。

例如：

- LLM 编造了网络测量值；
- Agent 使用了不合适的 Tool；
- Tool 返回异常，但 Agent 没有正确处理；
- Skill 的规则与当前网络条件不匹配；
- Agent 发现了一个异常，却错误地将其当作根本原因；
- 缺少关键证据，但 Agent 仍给出了确定结论。

说明问题可能出在哪里，以及如何进一步改进。

**实验结果不好并不意味着项目失败。能够准确发现 AI 系统的局限，并通过实验解释原因，也是重要的学习成果。**

### 第六部分：可运行系统与软件实现（建议 300–500 字）

完成一个能够实际使用的最小系统。

可以是：

- 命令行 Agent；
- Streamlit / Gradio 界面；
- 简单 Web 应用；
- 其他适当形式。

至少可以完成一次完整操作：

用户输入网络问题 → Agent 选择 Tool → 工具执行 → 返回证据 → Agent 形成结论。

本地 Ollama 或在线模型 API 均可使用，应说明运行条件、模型版本和依赖环境。

**必须提供至少两张真实运行截图：**

1. 用户输入和 Agent 的调查过程；
2. 工具调用、证据及最终结论。

需要展示源代码的组织结构、主要模块和程序入口。

可以使用 Trae、DeepSeek Harness 等工具辅助开发，但最终提交的程序必须能够由学生解释并复现。

### 第七部分：总结与学习反思（建议 200–400 字）

回答：

1. 本项目最重要的成果是什么？
2. Tool、Agent、Skill 分别起到了什么作用？
3. 哪个课堂知识真正解决了实际问题？
4. AI 在什么情况下表现较好？什么情况下容易出错？

### 评分原则

**原则一：不是 Agent 越多越好。**

不因使用 CrewAI、多 Agent 或复杂框架自动加分。单 Agent 如果能够可靠完成任务，也可以得满分。

**原则二：不是 LLM 调用越多越好。**

应鼓励 Agent 正确选择工具、减少无效调用，而不是设计复杂却没有必要的调用链。

**原则三：专业正确性比语言流畅更重要。**

不能因为 Agent 的解释听起来合理，就认为结论正确。必须检查公式、单位、假设、测量数据以及证据。

**原则四：Skill 必须有实际作用。**

仅提交一份很长的 Skill 文档，但 Agent 没有实际使用，或者无法说明它带来了什么改变，不能获得这一项的满分。

**原则五：评测比演示重要。**

一个成功 Demo 不能证明系统可靠。需要多种测试案例、合理对照，以及对失败的解释。

**原则六：课程学习优先于技术堆砌。**

允许使用 KNN、决策树、LR、GBDT、数据清洗和探索分析等知识，将机器学习模型作为 Agent 的一个 Tool。

但这些不是额外的强制要求。是否采用机器学习，应由项目实际需要决定。

## 七、其他要求

### 7.1 关于 AI 辅助开发

鼓励使用 Trae、DeepSeek Harness 及其他 AI 编程工具。

但应当清楚地区分：

- 哪些代码和设计是自己完成的；
- 哪些部分由 AI 协助生成；
- 自己如何测试、检查和修改 AI 的输出。

可以在附录中展示一段有代表性的 AI 协作过程，包括原始需求、AI 建议、发现的问题与最终修改。

不要求提交全部对话历史。

### 7.2 关于网络数据与安全

允许使用模拟拓扑、实验环境和公开数据。

不得未经授权扫描、攻击、修改或接管实际网络设备。

涉及网络配置变更的建议，应优先采用模拟执行或人工确认，不应让 Agent 在未经授权的情况下直接修改生产网络。

### 7.3 关于小组合作

鼓励小组合作。最多两人一小组，每组完成一个项目。

两位同学都应理解项目的主要设计、Tool 和 Skill 的实现，以及实验结果。

每个小组提交一份报告即可。报告中应详细说明成员分工和各自贡献。

### 7.4 关于已有课堂项目

此前完成的香农公式 Agent、信道质量评估与调制方式选择 Agent、汽车分类等项目，可以作为本次综合项目的基础。

但是，不能原样重复提交。

需要进一步扩展为具有明确用户场景、完整工作流程、工具调用、专业 Skill 和系统评测的综合应用。

## 九、最后想对同学们说

在这门课上，我们已经学会了向大语言模型提问，让它生成程序；也学会了利用 Agent 框架调用工具，把专业知识组织成 Skill。

但是，真正有价值的 AI 应用，并不是让大语言模型把一个答案说得更流畅。

当网络出现问题时，一个优秀的 AI Agent 应当像一位认真负责的工程师：

先理解现象，再提出假设；知道应该测量什么、计算什么；能够利用专业知识检查结果；愿意寻找反面证据；在证据不足时承认不确定性。

最后，给出一个有依据、能够帮助用户采取下一步行动的结论。

**这次项目，希望大家不只是学会让 AI 写程序，而是尝试把自己学过的通信网络知识，变成 AI 能够正确使用的专业能力。**

也希望大家通过自己的项目，真正体会到：

**AI 的价值，不是代替工程师思考，而是帮助工程师更有效地观察、分析、验证和解决问题。**
